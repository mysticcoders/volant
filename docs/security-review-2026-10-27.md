# Security implementation review — 2026-10-27

This is a risk-based repository review, not a penetration test or proof of absence of vulnerabilities. It covers CI, tracked dependency inputs, history secret detection, the network helpers and representative native trust boundaries. No release, website deployment, owner data mutation or live provider credential verification is part of this change.

## Tool decisions and researched basis

| Area | Decision for this repository | Why / evidence |
| --- | --- | --- |
| Secrets | **Gitleaks CLI** on every PR and weekly/manual, all fetched Git history, output redacted. | It scans Git history using configurable detection rules without needing to attempt provider logins. The [CLI documentation](https://github.com/gitleaks/gitleaks) documents history scanning, redaction and fingerprints. Use its open-source binary directly: the [Gitleaks Action wrapper](https://github.com/gitleaks/gitleaks-action/blob/master/v2.md) has organization licensing requirements that the CLI does not need. Binary version and SHA-256 are fixed in CI. |
| Second secret scanner | **Do not run both routinely.** Keep TruffleHog for an explicitly scoped incident or broader source inventory. | [TruffleHog](https://github.com/trufflesecurity/trufflehog) adds live credential verification and sources beyond Git, useful when triaging a real leak. Verification can contact providers with candidate credentials; verified-only output also does not replace detection of inactive/unverifiable secrets. Here, another routine gate adds maintenance and overlap without covering the larger native trust-boundary gaps. This is a repository-fit judgment, not a benchmark claiming Gitleaks detects more. |
| Dependencies | **OSV-Scanner 2.7.0** across every tracked supported lockfile; no package install or call analysis during scanning. | [Supported inputs](https://github.com/google/osv-scanner/blob/main/docs/supported_languages_and_lockfiles.md) include npm and Cargo, which match this mixed repository. Inputs are selected with `git ls-files`, not a recursive walk that can scan local worktrees or miss ignored directories. [OSV usage](https://google.github.io/osv-scanner/usage/) supports explicit lockfiles and machine-readable output. Scanner/network/schema failures fail closed. |
| pip-audit / npm audit | Use **npm audit as a corroborating triage check**, not a second duplicate CI gate. Defer pip-audit until Python build tooling is pinned. | [pip-audit](https://github.com/pypa/pip-audit) audits Python environments and requirements; it cannot replace npm/Cargo coverage. There is no tracked Python dependency input today. OSV plus reproducible inputs is a closer fit than auditing a random runner's Python environment. |
| Infrastructure | **zizmor** for the actual infrastructure present: GitHub Actions. Defer Trivy/Checkov. | [zizmor](https://docs.zizmor.sh/) specifically analyzes CI/CD, including [credential persistence and unpinned Actions](https://docs.zizmor.sh/audits/). There are no tracked Dockerfiles, Terraform, Kubernetes, Helm or CloudFormation inputs. Cloudflare worker configuration is embedded in `website/vite.config.ts`; do not count a generic IaC scan as auditing that account or deployment. [Trivy](https://trivy.dev/docs/latest/scanner/misconfiguration/) and [Checkov](https://www.checkov.io/1.Welcome/What%20is%20Checkov.html) are worthwhile when supported IaC/container artifacts are added. Neither establishes deployed Cloudflare configuration from this repo alone. |
| Website dynamic testing | **ZAP Baseline**, weekly/manual against an isolated locally built website, with JSON/HTML reports; the context excludes release downloads. | [Baseline documentation](https://www.zaproxy.org/docs/docker/baseline-scan/) specifies a one-minute spider followed by passive analysis, with distinct warning/failure/error exits. The job preserves those exits and is not part of PR gating initially; warnings are visible failures of this scheduled/manual job. It does not deploy, use production credentials or perform active attacks. An HTTP local result does not establish production TLS, CDN headers or custom-domain security. |
| Nuclei / Burp | Defer routine deployment; use curated Nuclei templates for a specific exposure or Burp for a scoped authenticated web assessment. | [Nuclei](https://docs.projectdiscovery.io/opensource/nuclei/overview) is template-driven and covers known exposures/protocols. [Burp Scanner](https://portswigger.net/burp/documentation/scanner) is web DAST with sophisticated state/authentication handling, and automated scanning requires [Professional or DAST](https://portswigger.net/burp/documentation/desktop/getting-started/running-your-first-scan). Neither benefit justifies adding another scanner to this small marketing site's baseline yet. |
| Native dynamic testing | Keep the existing isolated native/XPC/VM fixtures; add hostile-response regression tests at the rates boundary. | Web DAST does not exercise XPC caller identity, sandbox entitlements, Keychain denial, signed helper delivery, WASI isolation or TCC attribution. Existing `check-acp.sh`, `check-ai-http.sh`, `check-extensions.sh`, and the signed/disposable VM fixtures are the relevant layers. Fake transports, a build, and a web scan remain separate from signed installed-app evidence. |

## Gate policy and operation

`security.yml` is called by the PR workflow; all its PR jobs must succeed for `PR gate`. It also runs weekly and can be dispatched manually. Only its weekly/manual runs start the website baseline. All jobs use read-only repository permissions, no inherited owner secrets, pinned Action revisions, and a checksum-pinned Gitleaks/OSV binary. The ZAP image is pinned to the upstream Linux amd64 digest resolved on this review date. Scanner pins need deliberate upstream updates; a pinned scanner is not automatically current forever.

Dependency exceptions match **path + ecosystem + package + version + advisory ID**, expire on 2026-11-10, and leave the complete OSV report visible as a 14-day artifact. A new path, version or advisory cannot borrow an exception. Tests cover expiry at the deadline, new identity rejection, normalization and resolved debt. A green regression gate explicitly does not mean the initial vulnerabilities have been fixed.

Local commands:

```sh
gitleaks git --redact --no-banner --log-opts=--all
python3 tools/security-dependencies-tests.py
python3 tools/security-dependencies.py --scanner /path/to/osv-scanner
uvx zizmor==1.31.1 --offline --min-severity medium .github/workflows
actionlint
Scripts/test.sh --base origin/main
```

## Recurring lesson

- Symptom: native tests can pass while JavaScript adapters, website tooling and CI configuration accumulate vulnerabilities.
- Cause: functional test scope and macOS job selection are not security inventory or scheduled advisory monitoring.
- Prevention: independent security jobs, explicit tracked inputs, exact expiring debt, immutable scanner/Action versions, and retained reports. Never accept an empty/missing report as a successful scan or exclude entire fixture directories to silence candidates.
- Evidence: initial Gitleaks candidates were individually inspected; zizmor reproduced workflow problems and passes after correction; OSV queried seven explicit tracked lockfiles and reproduced 99 matches. Delivery/CI outcomes are recorded in the PR; a scheduled website baseline or signed native smoke must not be claimed merely because its job was added.
