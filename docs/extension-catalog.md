# Extension catalog

## Current behavior

Settings → Extensions has a **Catalog** section. Choosing **Check Catalog** fetches the signed index from
`https://mysticcoders.github.io/volant-extensions/`; Volant contacts it at no other time. Each listing
shows its name, version, summary, publisher, license and the permissions and hosts it declares, a
**Source** link to the exact reviewed revision, and **Install**, **Update**, **Installed** or **Bundled**.
Install and Update need **Allow Community Extensions** on.

The launcher has the same catalog as its own view, like Dictionary: choose **Extension Catalog**
(or type `catalog`, `store` or `marketplace` to find it), or type `catalog` directly. The view has its
own search field, the matching extensions on the left and the selected one's details on the right:
summary, notes, publisher, version, license, the permissions and hosts it needs, whether it is
installed and on, and a link to the reviewed source. Typing `catalog` opens the view but fetches
nothing; choosing the command, Check Catalog or Return loads the catalog once for the session. Search
matches name, ID, summary, publisher and hosts. Arrow keys move the selection; Return installs,
updates or uses the selected extension (it puts the name in the launcher's search field);
Command-Return opens its source; ⌘[ goes back. With community extensions off, Return opens
Extension Settings.
In Settings a single Refresh reloads installed extensions and, once the catalog has been checked,
checks it again.

Installing never turns an extension on, allows a host or runs code. The installed extension appears
under Installed, off, marked "From catalog", and its first use asks as usual. Removing it is the
existing **Uninstall…**, which moves the folder to the Trash, forgets its approval and prunes hosts no
other extension needs. Manually copied folders still work as before.

The first catalog holds the Hacker News and Lobsters readers from
[mysticcoders/volant-extensions](https://github.com/mysticcoders/volant-extensions).

## Format

`catalog.json` (format 1) is generated by `tools/catalog.py` in volant-extensions from each folder's
`manifest.json`, module and `listing.json` (summary, publisher, license, notes):

```json
{
  "format": 1,
  "sequence": 4,
  "generated": "2026-10-12T20:00:00Z",
  "revision": "<40-hex commit>",
  "extensions": [{
    "id": "community.volant.hn", "name": "Hacker News", "version": "0.1.0", "module": "hackernews.wasm",
    "summary": "…", "publisher": "Mystic Coders", "license": "MIT", "notes": "…",
    "abiVersion": 1, "capabilities": [], "hosts": ["hn.algolia.com"],
    "source": "https://github.com/mysticcoders/volant-extensions/tree/<revision>/hackernews",
    "manifest": {"sha256": "…", "size": 312}, "moduleFile": {"sha256": "…", "size": 61234}
  }]
}
```

A package is `packages/<id>/<version>/manifest.json`, `packages/<id>/<version>/<module>` and, when the
listing has `icon` and `iconFile`, `packages/<id>/<version>/<icon>` (a WebP of at most 32 KB that the
manifest names and pins). Volant 0.3.0 ignores the icon fields and downloads only the first two. Volant derives these paths itself; nothing in the index chooses a
path or a write location, and there is no archive to extract. IDs must be lowercase dotted labels (they
become the folder name), versions and module names path-safe, text bounded, capabilities known, and
hosts valid. At most 64 listings, a 256 KB index, 32 KB manifests and 2 MiB modules.

## Trust

- **Signature.** CI in volant-extensions signs the exact bytes of `catalog.json` with Ed25519 into
  `catalog.json.sig` (base64) and publishes the site to GitHub Pages. The private key exists only as the
  `CATALOG_SIGNING_KEY` Actions secret; `ExtensionCatalogKey` holds the public key. Anyone who can
  change that repository's `main` branch or workflow can get a catalog signed, so treat merge rights
  there as publishing rights.
- **Rollback.** `sequence` is the commit count of `main`. Volant records the highest sequence it
  accepted in `extension-catalog.json` beside config.json (per Mac, not synced) and refuses a lower
  one, so an old signed catalog cannot be replayed to offer superseded versions.
- **Packages.** Every downloaded file must match the listed size and SHA-256. The manifest must be
  valid and agree with the listing on ID, name, version, module, ABI, capabilities, hosts and module
  hash, and the module must declare bounded memory. A mismatch installs nothing.
- **Network.** The main app and extension helper still have no network access. `VolantFetchHost`
  gained `fetchCatalogFile`, which accepts only the index, its signature and package paths under the
  fixed base (checked again in the helper), refuses redirects, uses no cookies or cache, and stops at
  2 MiB.

## Installation

Files are written to a hidden `.staging-<uuid>` folder inside the Extensions folder, with a
`.volant-catalog.json` record of the catalog sequence, revision and source, then moved into place in one
step. An update moves the old folder to `.previous-<uuid>` first, puts it back if the move fails, and
deletes it after success. The catalog never replaces a bundled extension or an unrelated folder that
already uses the ID's name, and an update keeps the folder name of a manually installed copy.

Approval stays bound to the full manifest, so an update with changed code, permissions or hosts is
off until the owner enables it again; reinstalling identical bytes keeps their choice. Hosts only the
old version declared are pruned as for an uninstall. A run of that extension in progress is ended.

## Evidence

- `ExtensionCatalogTests` (Core): signature failure, rollback, unknown format, duplicate IDs, 25
  unsafe listing shapes, fixed paths only, size/hash mismatches, manifests that disagree with their
  listing, and unbounded memory.
- `ExtensionCatalogInstallTests` (app): a throwaway CryptoKit key and in-memory files cover signed
  loading, tampered and foreign signatures, the production key rejecting test signatures, derived
  download paths, atomic install without enabling, re-approval after a changed update, retained
  choice for identical reinstall, host pruning, a failed update restoring the previous version, and
  refusing tampered bytes, unrelated folders and bundled IDs.
- The native Actions fixture renders the catalog section with fictional listings, master switch on
  and off, in light and dark.

- The first published catalog (sequence 5, revision `6f2542f`) was fetched from GitHub Pages without
  redirects and decoded by `ExtensionCatalog.decode` with the production public key; both packages
  passed `Listing.verify` (October 12, 2026, a host-side script, not the app).
- A Settings layout fault found in those renders: catalog rows reused installed extension IDs as
  Form row identities, which misplaced Installed rows when a listed extension was installed. Catalog
  rows now use their own identity.

- The notarized 0.3.0 DMG, in the installed-acceptance VM, loaded the live catalog through the signed
  `VolantFetchHost` and installed both readers from Settings → Catalog without enabling them or
  allowing hosts (`tools/installed-acceptance/guest/extensions.sh`).

Not yet verified: Update in the signed app, which needs a second published version of a listed
extension.

## Remaining work

- Update discovery happens only when the owner checks the catalog; there is no background check or
  badge.
- No revocation list yet. Removing a listing stops new installs but does not flag installed copies.
  A future index field can mark revoked IDs or hashes for Settings to warn about and disable.
- Curate beyond the first two readers: text utilities such as Base64, URL encoding, UUIDs and JSON
  formatting, after reviewing source, license and maintenance. Native and adapted upstream
  extensions should be identified as such.
- Catalog hosting is GitHub Pages for now; moving it to usevolant.com would be a separate change to
  `ExtensionCatalog.baseURL` and the helper's check.

## Separate runtime follow-up

Measure fresh helper footprint, repeated execution peaks and settled memory across mixed modules using fictional inputs. Then decide whether an idle shutdown/recycle policy improves memory without unacceptable cold-start delay. Disabling community code must not interrupt a bundled command.

## Discovery quality decision

Symptom: installed extensions required a separate `ext` namespace despite being commands. Cause: only the explicit-prefix branch searched extension metadata. Change: merge direct metadata matches into ordinary launcher results, retain explicit-prefix compatibility and current activation gates. Avoid per-keystroke filesystem reads through metadata caching; invalidate on Settings/config refresh. Regression checks cover argument boundaries, Unicode/case preservation, discovery without executable bytes, explicit approval, app-name collisions and first-use navigation. Native fixtures render the affected launcher/Settings surfaces in light/dark appearances; signed installed-app execution remains separate evidence.
